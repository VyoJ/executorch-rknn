# RV1103/RV1106 and RKNN: what to know

Found on a Luckfox Pico Pro Max (RV1106) and Pico Mini B (RV1103) with
rknn-toolkit2 1.6.0 and the boards' own `librknnmrt.so` 1.6.0. Many of these
fail silently, and RKNN's x86 simulator runs models the board refuses, so
check every new operator on the board. What differs on the RV1103 is in
[rv1103.md](rv1103.md).

## What the NPU runs

- int8 only. int16 models build and run but give wrong results; float16 is
  refused.
- No LayerNorm, RMSNorm, ReduceMean, ReduceSum, Sqrt or Erf, and no CPU
  fallback for them on these chips: one such node stops the whole model.
  `GlobalAveragePool` works where `ReduceMean` does not.
- Activation x weight matmuls run (as convolutions); activation x activation
  matmuls, as in attention, do not.
- NPU memory is a CMA region set at boot: 66 MB on the Pro Max, 24 MB on the
  Mini B. Weights and activations of every loaded model live there, and RSS
  does not show them.

## Silent wrong results

- A `Conv` without an explicit `kernel_shape` gives wrong outputs. The
  attribute is optional in ONNX; the converter always emits it.
- A GlobalAveragePool over an unquantised input runs in float16 and comes out
  about a third too small. The partitioner leaves such a mean on the CPU.
- A 4-D reshape or transpose with a batch above 1 can become thousands of NPU
  tasks; `rknn_run` then fails after several seconds. The converter refuses
  them.
- RKNN drops a model output that the model also reads before a quantize, and
  merges two outputs that compute the same value. The blob records which
  `.rknn` output each delegate output reads.
- RKNN fuses a convolution with the SiLU after it and skips the int8 rounding
  between them, so a deep chain drifts from PT2E (closer to float, if anything).
- `optimization_level=2` reproduces PT2E exactly on shallow networks but made
  MobileNetV2 68% slower with the same accuracy; the default is 3.

## Things RV1106 refuses at build or run time

- A quantize/dequantize pair with nothing between them, or a second quantize
  of the same value (`unsupport cpu exDataConvert op`).
- A float16 input or output: an input not quantised straight away, or an
  output not produced by a dequantize. A convolution whose weight has no
  dequantize inside an otherwise quantised model fails to build.
- Calibration data for 4-D inputs must be NCHW `.npy`.

## Memory layouts and the runtime API

- Only the zero-copy API (`rknn_create_mem`, `rknn_set_io_mem`) exists.
- Inputs are NHWC with rows padded to `w_stride`, except that inputs with a
  channel count other than 1, 3 or 4 are NC1HWC2, padded to 16 channels, and
  report the padded size even in the logical attributes.
- Pre-quantised inputs need `pass_through = 1`, or the runtime converts them
  again.
- 4-D outputs can only be bound in their native NC1HWC2 layout, where H and W
  may be reported flattened and padded: a [1, 10, 15, 14] output came back as
  dims [1, 2, 1, 212, 16] with `w_stride` 14.
- Writing an output buffer from the CPU before a run corrupts the NPU's
  results, even with `rknn_mem_sync` afterwards.

## The CPU side

- One Cortex-A7 core with NEON and VFPv4, GCC 8.3 and uClibc 1.0.31. A second
  program running at the same time halves any timing.
- ExecuTorch's portable kernels build with one patch (GCC 8 cannot parse
  `[[maybe_unused]]` on the first parameter of an explicit constructor).
- XNNPACK needs two: its ARMv6 SIMD32 kernels need types GCC 8 lacks, and
  cpuinfo only reads CPU features through glibc's `getauxval`. uClibc reports
  itself as glibc 2.2 and has no `getauxval`, so cpuinfo saw no FPU and
  XNNPACK refused to start. The patch reads `/proc/self/auxv` instead.
- ExecuTorch's optimised kernels need C++20 and do not build with GCC 8.
- The board's adbd does not return a command's exit status; the scripts check
  for output files instead.
